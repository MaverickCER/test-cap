test-cap: a one-page brief

test-cap signs people in to the owner's apps with two factors by default, and records how strongly each session was proven.

The problem

The previous library published 49 advisories in about 23 months and patches only its latest release. Its clock cannot be controlled in tests.

What it does

It serves sign-up, sign-in, TOTP and sessions. On Express, fetch and TanStack Start, it protects every route that is not listed as public. It sends an OCSF security event for each sign-in.

Why it matters

  • On Express, fetch and TanStack Start, a route someone forgot to protect is protected anyway.
  • Each session says which factors proved it, so a sensitive action can ask for more.
  • The owner decides when to patch, because the code is the owner's.

What it costs

An app adds one adapter line, a store over its database and two keys. Each person enrols a second factor at sign-up.

What could go wrong

  • test-cap is pre-1.0 and has not cut its first release. Before 1.0, a minor release may break the API (VERSIONING.md). It is phase 3 of 9: passwords and TOTP are the only sign-in methods so far.
  • It is phase 3 of 9, so passkeys, email recovery and social sign-in are not built yet.
  • No durable store is exported yet, so it is ready for development and tests only.
  • There has been no external penetration test, by the owner's decision.

What we are asking for

Agree that new work in the owner's apps uses test-cap once a durable store is exported.
