# Attack catalogue

Each attack test-cap is designed against, the design element that stops it, the negative test that proves it, and
the security invariant it breaks. Flows (F01–F22) and the attacker model are in [threat-model.md](threat-model.md);
each design element is owned by the ADR named in its row, under [decisions/](decisions/); each invariant is in
[security-invariants.md](security-invariants.md). Terms follow the [glossary](../GLOSSARY.md).

## How a docs test enforces this file

A docs test (`test/docs/attack-catalogue.test.ts`) reads every table below and fails when any of these is false:

- **Ids are stable.** Each id is unique and kebab-case. An id is never renamed or reused; a retired attack keeps its
  row with a reason.
- **Every entry names its test.** The Test column is exactly `test/attacks/<id>.test.ts`. A `not applicable` row
  says `none` in the Test and Phase columns; its Stopped-by cell gives the reason and the entry that tests the
  transferable class, if one does.
- **Status is honest.** Status is `planned`, `tested` or `not applicable`. A row may say `tested` only once its test
  file exists, and a test file under `test/attacks/` must have a row. Every row is `planned` or `not applicable` on
  2026-11-15.
- **The threat model and the catalogue agree.** Every id the threat model cites exists here, and every `planned` or
  `tested` id is cited by at least one flow there. `not applicable` rows are exempt: they name no test-cap flow.
- **Sources stay covered.** All 49 Better Auth repository advisories appear in a Source cell.
- **ADRs exist.** Every ADR number named in Stopped-by exists under `specs/decisions/`.
- **Every tested entry names its invariant.** The Invariant column names the security invariants that list the entry
  in [security-invariants.md](security-invariants.md). A `tested` row names at least one, a `not applicable` row says
  `none`, and a `planned` row says `none` until an invariant lists it. `test/docs/security-invariants.test.ts` checks
  the column against the registry in both directions.

The phase that implements an entry's design element flips the row to `tested` in the same pull request. Release
verification (phase 9) requires every `planned` row to be `tested`; that is the plan's done-when "every attack entry
has a test".

## Sources and abbreviations

- **BA**: Better Auth repository advisories, <https://github.com/better-auth/better-auth/security/advisories>: 49
  published as of 2026-11-15, cited by GHSA id.
- **SAML libraries**: the GitHub advisory database and repository advisories for `@node-saml/node-saml` (and
  `passport-saml`), `xml-crypto`, `@xmldom/xmldom` and `samlify` (rejected, ADR 0028, but its classes still apply).
- **SWA**: `@simplewebauthn/server` repository advisories.
- **ASVS**: OWASP ASVS 5.0.0 requirement ids from V2 (anti-automation), V6, V7, V10 and V16. ASVS requirements that are not attacks (for
  example, that users can change their password) are traced in `specs/requirements.md` (ADR 0017), not here.
- **OWASP**: the Authentication (Auth CS), Session Management (Session CS) and Forgot Password (Reset CS) cheat
  sheets.
- **NIST**: SP 800-63B-4 sections as quoted in `Dev/auth-cap-design/research-2026-11-15.md`.
- **Classic**: the attacks the plan lists by name: fixation, token leakage in URLs and Referer, timing, Host
  poisoning, cookie tossing, downgrade, recovery below the account's level, redemption races, and parsing differences
  between an adapter and the core.

`O1`–`O16` in a row point to the threat model's [Open](threat-model.md#open) items: the row tests the recommendation
until the owner decides.
