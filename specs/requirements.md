# Requirement mapping

This file maps test-cap's design to two outside standards: the OWASP ASVS 5.0.0 chapters on authentication, sessions,
tokens, OAuth and OIDC, and logging, and the SHALL statements of NIST SP 800-63B-4 that bind a verifier and session
manager. ADR 0017 governs it. It is engineering traceability for internal readers: it records which design element is
meant to meet each requirement, what is still missing, and which test will pin it. Each row says which
design decision a requirement "maps to" and which test will pin it.

Status: accepted (2026-11-15), written in phase 1 (Design). Phases 2 to 4 have built part of it since. A row's status
says what the design meets; a named test that does not exist yet is planned, and the requirement is proven only once its
test exists. Each is written in the phase that builds its capability. The recommendations under [Open](#open) are provisional
defaults until the owner decides.

## How to read a row

Each row is one requirement. The columns are:

- **Id.** The ASVS requirement id, or the 800-63B-4 section number (`§3.1.1.2`). Several SHALL statements from one
  section may share a row when they share a status.
- **Requirement.** A short paraphrase. The source text is authoritative; see [Sources](#sources).
- **Level.** The ASVS level (L1, L2, L3), or for NIST the assurance level the statement binds (AAL1, AAL2, AAL3, or
  `all`).
- **Status.** One of four words:
  - `met by design`: the plan's design meets the requirement, and the planned test will prove it;
  - `partly met`: part of the requirement is met; the last column states the gap, usually as an [Open](#open) item;
  - `not applicable`: the requirement concerns something test-cap does not do; the last column says why;
  - `out of scope`: the requirement is real but belongs to another owner, named in the last column: the app,
    secure-cap or access-cap.
- **ADR.** The decision record or records in `specs/decisions/` that own the design element.
- **Planned test.** One or more paths under `test/`, or `none:` followed by the reason no test-cap test can exist.
- **Gap, reason or owner.** For `partly met`, the gap. For `not applicable`, the reason. For `out of scope`, the owner.
  For `met by design`, any limit worth knowing.

A docs test, `test/docs/design-traceability.test.ts`, reads every table in this file and fails when a row lacks a
status from the four above, an existing ADR number, or a planned test path (or a `none:` reason). ADR 0017 lists the
checks it adds later: a gap for every `partly met` row and an owner for every `out of scope` row.

## NIST SP 800-63B-4

Each row holds one SHALL or SHALL NOT, or several from the same section that share a status. test-cap acts as verifier,
credential service provider (CSP) and session manager in one process, and supports passwords, look-up secrets
(recovery codes), single-factor OTP (TOTP), and single-factor and multi-factor cryptographic authenticators (security
keys and passkeys).

Left out: SHALL statements addressed only to federal agencies (FIPS 140 for federal verifiers, SAOP, SORN and PIA
duties, federal enterprise sync fabrics), the internals of biometric systems (§3.2.3.1 to §3.2.3.4), and requirements
on the inside of an authenticator or its connection to a device. Rows below mark the closest of these `not applicable`
where a reader would look for them.

## Open

Questions the plan leaves unsettled, each with a recommendation. Items that another ADR already lists are referenced
there, not repeated: ADR 0010 Open 1 (context-specific words), ADR 0013 Open 2 (delegation credential format), ADR 0021
Open 1 (what an email sign-in session holds) and Open 2 (magic links and mail scanners), ADR 0025 Open 1 (passkey first
versus enumeration).

1. **What happens at 100 failures.** NIST §3.2.2 caps consecutive failures per authenticator at 100 "by disabling that
   authenticator", and a disabled authenticator must be bound again. The plan says "throttle, never lock out". The two
   meet only if disabling one authenticator is not counted as locking out the account. Recommendation (ADR 0009):
   escalating delays below the cap; at the 100th consecutive failure, disable that authenticator only, keep the account
   reachable through its other authenticators and recovery, emit an event, and state in ADR 0009 that someone who knows
   an identifier can disable its password this way. A successful ceremony resets only the counters of the
   authenticators it used.
2. **Password minimum and how length is counted.** Resolved: ADR 0010 now owns every password-verifier rule (section
   5): 8 code points after NFC within MFA, 15 when a deviation lets a password alone pass, 256 maximum.
3. **Acting on a later compromise.** NIST §3.1.1.2 requires a forced change when there is evidence of compromise.
   ADR 0010 Open 2 re-checks only `indeterminate` results. Recommendation: re-check every password against HIBP at
   successful password sign-in, and on a match put the session in the recovery state until a new password is set.
4. **Password change asks for the current password** (ASVS 6.2.3). Recommendation: the change form asks for the
   current password; an account with no password that adds one does so behind the fresh ceremony of Open 8.
5. **Recovery-code rules** (ADR 0007). NIST §3.1.2.1, §3.1.2.2 and §4.2.1.1, and ASVS 6.5.2, together require four
   things. ADR 0007 §1 now decides two: codes are generated only from an AAL2 session, and each is stored as argon2id
   with its own salt, selected by a short public prefix. Still open: a new code issued after each use, and a recovery
   notification for every replacement. Recommendation: both.
6. **Recovering an AAL2 account** (ADR 0007). NIST §4.2.2.2 needs two recovery codes obtained by different methods, or
   one code plus a still-bound single-factor authenticator. Recommendation: an email-issued code alone never completes
   recovery of an account that can reach AAL2; it must be paired with a saved recovery code or a successful ceremony
   with a still-bound authenticator (password, TOTP or passkey). A password reset by someone who can still pass AAL2
   is binding a new authenticator (NIST §4.2), not recovery.
7. **Telling the person** (ADR 0015). NIST §4.1.2.1, §4.2.1.1, §4.2.1.2, §4.2.3 and §4.6, and ASVS 6.3.5 and 6.3.7, ask
   for messages to the subscriber, at least two notification and recovery addresses, and repudiation instructions with
   contact details. The plan sends events to the app's `onEvent` only. Recommendation: test-cap sends notifications
   through `sendEmail` when an authenticator is added or removed, a password changes, a recovery completes or recovery
   codes are replaced; an account may hold a second confirmed address; message text comes from `messages`, and the
   contact details from configuration.
8. **A fresh ceremony for credential and account changes** (ADR 0005). ASVS 7.5.1 and 7.5.2 and NIST §4.1.2.1 ask for
   reauthentication before adding or removing authenticators, changing the email address, issuing recovery codes or
   ending other sessions. Recommendation: a built-in requirement, `account.credentials`, met by a ceremony at the lower
   of the account's highest level and the new authenticator's level, completed in the last 10 minutes.
9. **Numbers the plan does not fix.** Recommendations:
   - TOTP (ADR 0027): a 160-bit secret, HMAC-SHA-1, 6 digits, a 30-second step, accepting the current step and the one
     before. Accepting the previous step stretches ASVS 6.5.5's 30 seconds to at most 60; the alternative, the current
     step only, meets it at a cost to people with slow typing or clock drift.
   - Passkey challenge (ADR 0016): 256 bits.
   - Email sign-in code or link (ADR 0021): 10 minutes, as ASVS 6.5.5 asks.
   - Concurrent sessions (ADR 0006): no limit by default, stated in the policy report; an optional limit revokes the
     oldest session and emits an event.
   - OIDC scopes (ADR 0016): `openid` and `email`, plus any an issuer's trust-config entry adds.
10. **Binding an email sign-in code to its request** (ASVS 6.6.2, ADR 0021). Recommendation: the code or link is bound
    to a server-side transaction for the browser that asked; a link opened elsewhere reaches the confirmation page of
    ADR 0021 Open 2 and signs in only that browser after its `POST`.
11. **ID token signatures and algorithms** (ASVS 6.8.2, 9.1.1, 9.1.2). Settled: ADR 0016 §7 calls
    `validateApplicationLevelSignature` on every ID token, against a per-issuer algorithm allowlist in the trust config
    that excludes `none` and symmetric algorithms.
12. **Reauthentication restarts the absolute timeout** (NIST §5.2, ADR 0006). Recommendation: a successful
    reauthentication or step-up sets a new absolute expiry from its own time, capped by the level's limit.
13. **A custom `RandomSource` in production** (NIST §3.2.12, ASVS 6.5.3). Settled: ADR 0026 §4 refuses to start with
    a custom `Clock` or `RandomSource` in any mode but `test`, and ADR 0003 §7 says so.
14. **Events for tripped controls** (ASVS 16.3.2 to 16.3.4, ADR 0015). Recommendation: emit events when throttling
    engages, an origin or CSRF check fails, a state, nonce or PKCE check fails, a used code is replayed, HIBP or an IdP
    is unreachable, and when `auth.require` answers anything but `allow` (OCSF Authorize Session 3003, which the
    research note lists and the plan does not use).
15. **Admin reset and global revoke** (ASVS 6.4.6, 7.4.5, ADR 0014). Recommendation: an admin call that ends a user's
    sessions and puts the password authenticator in a must-change state reached only through recovery, so the
    administrator never sees or chooses a password; and an admin call that revokes every session in a tenant.
16. **API-key expiry reminders** (ASVS 6.4.5, ADR 0013). Recommendation: the key listing shows each key's expiry, and
    the policy report counts keys that expire within 14 days.
17. **FIPS 140 at AAL3** (NIST §2.3.2, ADR 0005). test-cap cannot check FIPS validation of an authenticator or of the
    runtime's crypto module. Recommendation: the policy report states that test-cap's AAL3 does not check either, and
    that an app needing it narrows the attestation roots to validated models and runs a validated runtime build.
