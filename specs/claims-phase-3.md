# Claims audit: phase 3

Every factual claim in the human-facing documents phase 3 adds or changes, paired with the evidence that fails when
the claim becomes false. Of 326 claims, 235 are backed as written, 86 were narrowed to what the
evidence proves, and 5 were removed. Rows 315 to 326 audit the request limits phase 4 adds (ADR 0009 §8) by the
same rules.

## Scope and rules

The audit covers `README.md`, `GUIDE.md`, `ADOPTION.md`, `VERSIONING.md`, `docs/site.json` (the source of
`docs/index.html` and `docs/brief.html`), `examples/*/README.md`, every `.changeset/*.md`, and the prose of
`specs/architecture.md`. ADRs are out of scope. The rules are metric 9 of the success definition:

- A functional claim needs a behavioural test; a security claim needs a negative test and a security invariant.
- A runtime claim needs a CI job. A performance claim needs a benchmark or a pinned parameter test.
- A protocol claim needs a specification and a conformance test.
- An architecture or design claim needs an ADR, and a test where the claim is about runtime behaviour.
- A planned feature is labelled with its phase. A claim wider than its evidence is narrowed; a claim no evidence can
  back is removed.

A status of `narrowed` means the wording changed in this audit; the claim cell says what it was. `File:line` points at
the claim after the change. A removed claim names the file it left.

`test/docs/claims-phase-3.test.ts` checks that every test file and test name in the table exists. It also checks
each CI job against `.github/workflows/contract.yml` and each invariant against `specs/security-invariants.md`. A test
name with `%s`, `%j`, `$name` or a similar placeholder is the parameterised name as written in the test file.

## Limits of this audit

- Line numbers are correct for the tree this audit was written against; later edits move them. The docs test does not
  check them.
- The audit pairs each claim with evidence; it does not re-run mutation. The evidence tests are the ones the full gate
  runs.
- Background claims about Better Auth rest on the research note ADR 0001 cites, not on a test here.
- `AGENTS.md` is generated from `docs/surface.json` and is outside this audit. Its `test-cap/fetch` row still says
  "any runtime with the Web Request and Response globals: Node, Bun and Deno", which is wider than the Node-only tests.
- ADR 0024 and ADR 0003 still place the Nest adapter in phase 6; the success definition and
  `specs/security-invariants.md` place it in phase 4. The documents here follow phase 4 and await the owner's ADR fix.
